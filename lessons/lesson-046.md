## About this chapter

Chapter 46 is a complete SQL injection lab. It explains what SQL injection is, why it happens, sets up DVWA as a practice target, runs a first SQLMap test, shows how to read the results and the real impact, and finishes with the developer defences that actually prevent it.

## What you will learn

- What real-world impact SQL injection can have
- How parameterised queries and least privilege prevent it

## Important concepts

### Data becomes code

SQL injection occurs when user input is concatenated into a query so the database treats part of the input as SQL syntax. Parameterised queries keep data and code separate, which is the primary fix.

### SQLMap automates confirmation and extraction

SQLMap sends crafted requests, compares responses and identifies injection techniques. Because it can generate heavy traffic and extract data, it belongs only in a lab or an explicitly authorized engagement.

## Practical notes

All demos target DVWA on your own VM. Replace the URL, cookie and parameters with your lab values.

| Command | What it does |
| --- | --- |
| `sqlmap -u "http://dvwa.local/vulnerabilities/sqli/?id=1&Submit=Submit" --cookie="PHPSESSID=...; security=low"` | Test a lab parameter with the session cookie. |
| `sqlmap -u "URL" --batch` | Accept default answers for automation. |
| `sqlmap -u "URL" --dbs` | Enumerate databases after confirming injection. |
| `sqlmap -u "URL" -D dvwa --tables` | List tables in a specific database. |

Commands are shown for study. Run them only in your own lab, read the manual page (`man <tool>`) first, and check every option before executing anything.

## FAQ

### How do developers prevent SQL injection?

Use parameterised queries or an ORM, enforce least-privilege database accounts, hide detailed errors, and validate input as defence in depth.

### Can SQLMap test any website?

Technically it can send requests, but doing so without permission is unauthorized access. Only test your own lab or systems within a written scope.
