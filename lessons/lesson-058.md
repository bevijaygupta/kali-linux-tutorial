## Important concepts

### Every attempt is visible

An online attack sends authentication requests to a live service. That creates logs, triggers alerts and is constrained by lockout policies. Hydra's speed cannot overcome a server that stops answering after five failures.

### Form attacks depend on request shape

Web login modules need the correct form path, field names and failure string. A single mismatch produces false negatives, so capture a real request from your lab app and verify one known-good credential first.

## Practical notes

Use only lab services you own. Hydra syntax follows the service module, target, user and password list.

| Command | What it does |
| --- | --- |
| `hydra -l admin -P passlist.txt ssh://192.168.56.101` | Test SSH credentials against a lab host. |
| `hydra -L users.txt -P passlist.txt ftp://192.168.56.101` | Test FTP credentials with user and password lists. |
| `hydra -l admin -P passlist.txt 192.168.56.101 http-post-form "/login.php:user=^USER^&pass=^PASS^:F=Invalid"` | Test a lab web form; field names and failure text must match your app. |

Commands are shown for study. Run them only in your own lab, read the manual page (`man <tool>`) first, and check every option before executing anything.

## FAQ

### Why is Hydra slower than offline cracking?

Each guess requires a network request and a server response, and defences such as lockouts or delays limit attempts.

### Why does my web form attack report zero results?

The form path, parameter names or failure indicator is probably wrong. Verify with a browser request and a known credential first.
