## About this chapter

Chapter 36 covers DNStracer, which follows a DNS query from the root servers through the TLD to the authoritative name server. It explains how to read that path, why it is useful during reconnaissance, and how it complements the subdomain tools from the previous two chapters.

## What you will learn

- What DNStracer does differently from subdomain discovery tools
- How a DNS query travels from root to authoritative servers
- How to run DNStracer against a domain
- How to read the delegation path in the output
- When tracing DNS is useful during reconnaissance
- How DNStracer fits with Dnsenum and DNSmap

## Important concepts

### Delegation is a chain

Resolving a name starts at a root server, which refers the resolver to the relevant TLD servers, which refer it to the domain's authoritative servers. DNStracer displays these hops, making misconfigurations and unusual hosting arrangements visible.

### Reconnaissance context

Understanding which provider hosts a domain's DNS can reveal shared infrastructure or outsourcing relationships. That context helps interpret other findings and avoid testing infrastructure outside scope.

## Practical notes

Trace a domain you own or a public example domain.

| Command | What it does |
| --- | --- |
| `dnstracer example.com` | Trace the DNS resolution path for the domain. |
| `dnstracer -s . example.com` | Start the trace explicitly from a root server. |
| `dnstracer -v example.com` | Show more detail about each hop. |

Commands are shown for study. Run them only in your own lab, read the manual page (`man <tool>`) first, and check every option before executing anything.

## FAQ

### Does DNStracer find subdomains?

No. It traces how a specific name resolves through the DNS hierarchy. Use Dnsenum or DNSmap for subdomain discovery.

### Why does the trace show a third-party provider?

Many organizations delegate DNS to a hosting or CDN provider. That delegation is useful context for mapping infrastructure.
